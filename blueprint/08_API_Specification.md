# EWES
## Spécification API REST
### Version 1.0 | Statut : Draft

---

# 1. Conventions

Chemin de base `/api/v1` ; JSON UTF-8 ; dates ISO-8601 UTC ; jeton d'accès porteur (bearer) pour les routes protégées ; documentation OpenAPI générée depuis le code source (Swagger NestJS) et publiée sur un chemin non indexé. Les listes utilisent `page`, `limit`, des filtres/tri explicites et renvoient `data` + `meta`. Les mutations renvoient la représentation courante de la ressource.

# 2. Contrat d'erreur

```json
{ "code": "DOCUMENT_ACCESS_FORBIDDEN", "message": "Vous n'avez pas accès à ce document.", "details": [], "requestId": "..." }
```
Les erreurs de validation renvoient des détails de champ exploitables par le client : `details: [{ "field": "email", "messages": ["…"] }]` (pipe global `createValidationPipe`). Le frontend ne doit jamais interpréter un message humain pour piloter une logique.

# 4. Règles de mutation

`POST /realisations`, `POST /articles` et toute mutation de publication vérifient les droits du rôle avant écriture ; le passage d'un statut `DRAFT` à `PUBLISHED` est une action explicite (jamais un effet de bord d'une simple sauvegarde). `POST /documents-prives/files` valide le type/la taille de fichier et exige un `folderId` existant avec confidentialité résolue. `POST /contact` est accessible sans authentification mais protégé contre la soumission automatisée (limitation de fréquence). Toute route retournant un fichier privé vérifie le droit d'accès à chaque requête — jamais via une URL statique non contrôlée.

# 5. Sécurité et compatibilité

RBAC et vérification de propriété/droit s'appliquent à chaque endpoint protégé. Ne jamais exposer un hash de mot de passe, un jeton de rafraîchissement, ou un chemin de fichier privé non vérifié. Tout changement cassant nécessite une nouvelle version d'API (`/api/v2`).

> Note (2026-10-03) — **Pages et services.** `GET /pages/:slug` renvoie aussi `metaDescriptionFr/En`. `GET /services[/:slug]` renvoie `imageUrl`, `imageAltFr/En` et, par prestation, `icon`. Admin : `PUT /admin/services/:id/offerings/order` (`{ ids }` : liste complète des prestations du service, appliquée d'un bloc, `400 SERVICE_OFFERING_ORDER_MISMATCH` sinon) ; une prestation ou un service créé sans `sortOrder` se range en dernier ; `imageUrl` est validé contre la médiathèque (`400` si l'adresse n'est pas `/uploads/<nom>`, `404 MEDIA_NOT_FOUND` si l'image n'existe pas, `null` la retire) ; `icon` : minuscules, chiffres et tirets (un nom inconnu du site retombe sur un pictogramme par défaut). Publier/dépublier une page ou un service est audité (`PAGE_PUBLISHED|UNPUBLISHED`, `SERVICE_PUBLISHED|UNPUBLISHED`, avant/après et acteur ; une action sans effet n'écrit rien) ainsi que le retrait d'une prestation (`SERVICE_OFFERING_REMOVED`). Pas de suppression ni d'archivage d'une page ou d'un pôle.

> Note (2026-10-03) — **Chiffres clés.** Public : `GET /key-figures` → `{ data: [{ value, suffixFr/En, labelFr/En, subtextFr/En }] }` (visibles seulement, dans l'ordre ; `value` déjà calculée ; ni identifiant, ni `sinceYear`, ni visibilité). Admin (`ADMINISTRATEUR`/`GESTIONNAIRE`) : `GET|POST /admin/key-figures`, `PATCH|DELETE /admin/key-figures/:id`, `PUT /admin/key-figures/order` (liste complète, `400 KEY_FIGURE_ORDER_MISMATCH` sinon) ; la réponse admin ajoute `displayedValue`. Un chiffre créé se range en dernier ; `409 KEY_FIGURE_LIMIT` au-delà de 8 ; `400 KEY_FIGURE_YEAR_IN_FUTURE` ; `sinceYear: null` repasse en valeur fixe. Création, modification et suppression sont auditées (`KEY_FIGURE_CREATED|UPDATED|DELETED`, avant/après : libellé, valeur, année de départ, visibilité). Tag de cache du site : `key-figures`.

> Note (2026-10-03) — **Chiffres clés : `source`.** `POST|PATCH /admin/key-figures` acceptent `source` (`FIXED` par défaut) ; `YEARS_SINCE` exige `sinceYear` (`400 KEY_FIGURE_YEAR_REQUIRED`, `KEY_FIGURE_YEAR_IN_FUTURE`), l'année envoyée avec une autre source est ignorée. `GET /admin/key-figures/counts` → `{ missions, trainings }` (nombres actuels, pour l'aperçu du portail). La lecture publique ne révèle pas la source. Le site rafraîchit ses chiffres sur les étiquettes `key-figures` **et** `realisations`.

> Note (2026-10-03) — **Experts.** Public : `GET /experts` → `{ data: [{ fullName, roleFr/En, bioFr/En, specialtiesFr/En, yearsOfExperience, photoUrl, poleSlug }] }` (publiés seulement, dans l'ordre ; ni identifiant, ni statut). Admin (`ADMINISTRATEUR`/`GESTIONNAIRE`) : `GET|POST /admin/experts` (création toujours en brouillon, en dernière position), `GET|PATCH|DELETE /admin/experts/:id`, `POST /admin/experts/:id/publish|unpublish`, `PUT /admin/experts/order` (liste complète, `400 EXPERT_ORDER_MISMATCH` sinon). Un statut envoyé par le client est refusé ; `photoUrl` est validé contre la médiathèque (`404 MEDIA_NOT_FOUND`, `null` la retire) ; `serviceId` inconnu : `400 EXPERT_SERVICE_NOT_FOUND` ; spécialités nettoyées (espaces, vides, doublons) et limitées à 12. Publication, dépublication et suppression sont auditées (`EXPERT_PUBLISHED|UNPUBLISHED|DELETED`) ; une action sans effet n'écrit rien. Tag de cache du site : `experts`.

> Note (2026-10-03) — **Utilisateurs & rôles** (`ADMINISTRATEUR` uniquement ; le rôle vient du jeton, jamais du corps). `GET /admin/users` (comptes non supprimés, avec `lastActiveAt` = dernière session ouverte), `GET /admin/users/:id` (ajoute `activeSessions` et `grants { folders, documents }`), `PATCH /admin/users/:id/role` `{ role }`, `POST /admin/users/:id/deactivate|reactivate` (idempotents). Invitations : `GET|POST /admin/users/invitations` (`{ fullName, email, role }` → `{ invitation, activationUrl }`), `POST /admin/users/invitations/:id/resend` (nouveau jeton, l'ancien cesse de fonctionner ; `429 INVITATION_RECENTLY_SENT` sous 60 s), `DELETE /admin/users/invitations/:id`. Erreurs : `409 USER_EMAIL_TAKEN`, `409 INVITATION_PENDING`, `403 CANNOT_CHANGE_OWN_ROLE`, `403 CANNOT_DEACTIVATE_SELF`, `409 LAST_ADMINISTRATOR` (il reste toujours un administrateur actif), `400 ROLE_UNCHANGED`, `409 CONCURRENT_UPDATE` (transaction sérialisable à rejouer). **`activationUrl` n'est renvoyé qu'à l'invitation et au renvoi, jamais relisible** (secours si l'e-mail n'arrive pas). Public, limité en fréquence : `POST /auth/invitations/inspect` `{ token }` → `{ email, fullName, role, expiresAt }` (`404 INVITATION_INVALID` jeton inconnu ou retiré, `410 INVITATION_EXPIRED`, `410 INVITATION_USED`) et `POST /auth/invitations/accept` `{ token, password }` → mêmes jetons que `POST /auth/login` (le compte prend le rôle de l'invitation ; tout autre champ est refusé). Mot de passe : 12 à 128 caractères, différent de l'adresse e-mail. Audit : `USER_INVITED`, `USER_INVITATION_RESENT`, `USER_INVITATION_REVOKED` (entité `UserInvitation`) ; `USER_INVITATION_ACCEPTED`, `USER_ROLE_CHANGED` (avant/après du rôle), `USER_DEACTIVATED`, `USER_REACTIVATED` (entité `User`).
